## 1. 이번 작업의 완료선

C2-2에서는 **물풀 미로의 이동 규칙만** 구현한다.

1. 물결북 반응 뒤 물풀문이 열린다.
2. 미로 안에서 얕은 물·깊은 물·물살·안전 지점을 서버 지역 데이터로 구분한다.
3. 서버가 물살 적용과 최종 위치를 판정한다.
4. 깊은 물에 들어가면 마지막 안전 지점으로 되돌린다.
5. 새로고침·재접속과 다인 플레이에서도 각 플레이어의 안전 위치가 독립적으로 유지된다.
6. 전달된 물풀문·물살 에셋을 런타임에 연결한다.

젖은 실밥이, 전투, 물들이 구조, 안전 물길 영속화, `CH02_MAZE_CLEARED`는 C2-3 범위이므로 시작하지 않는다.

## 3. 진행 사건과 문 상태

물결북 사건 `lake_wave_drum_awakened`가 완료되면 서버가 미로 입구 개방 사건을 한 번 기록한다. 사건 이름은 다음으로 고정한다.

```text
lake_safe_route_opened
```

- 선행 사건이 없으면 직접 요청을 거부한다.
- 직렬·동시 중복 요청은 멱등 처리한다.
- 닫힌 상태에는 `reed-gate-closed`, 열린 상태에는 `reed-gate-open`을 같은 좌표와 피벗에 표시한다.
- 통행 가능 여부는 서버 사건과 서버 충돌 계약으로 판정한다. 클라이언트 텍스처 상태로 판정하지 않는다.
- C2-2의 끝에 새 장 체크포인트나 `CH02_MAZE_CLEARED`를 기록하지 않는다.

기존 임시 미로 표식은 제거한다.

## 4. 서버 지역 데이터 계약

`BE/story-data/save-a-turby/stages/lake.json`과 기존 지역 데이터 로더·검증기를 확장한다. 이름은 기존 코드 관례에 맞출 수 있지만 아래 의미는 보존한다.

```text
waterAreas[]
  id
  kind: shallow | deep
  bounds 또는 polygon

currentFields[]
  id
  bounds 또는 polygon
  direction: 정규화 가능한 벡터
  pushDistancePx
  cooldownMs
  requires / unless

safeAnchors[]
  id
  x, y
  radius
```

필수 검증:

1. 모든 구역·앵커·물살 목적지는 `3200×2400` 안이다.
2. ID가 중복되지 않는다.
3. 물살 방향은 영벡터가 아니다.
4. 물살 목적지가 blocker, 닫힌 문, 깊은 물과 겹치면 가장 가까운 통행 가능 지점으로 보정한다.
5. 클라이언트가 물살 ID·방향·거리·목적 좌표를 결정하지 않는다.
6. 서버 응답에는 권위 위치와 적용한 `currentFieldId` 또는 `null`을 포함한다.
7. 기존 일반 이동·충돌 검증을 우회하지 않는다.

## 5. 이동 수치와 난이도

저학년 사용자가 실패 부담 없이 반복할 수 있게 다음 값으로 구현한다.

| 항목 | 값 |
|---|---:|
| 약한 물살 밀림 | 64px |
| 강한 물살 밀림 | 88px |
| 같은 물살 재적용 대기 | 1,200ms |
| 연속 적용 상한 | 2회 |
| 깊은 물 경계 여유 | 플레이어 반지름 + 12px |
| 안전 복귀 뒤 물살 보호 | 1,500ms |

- 물살과 깊은 물은 HP·아이템·진행도 손실이나 실패 상태를 만들지 않는다.
- 미로 초반은 약한 물살만 사용한다.
- 강한 물살은 같은 화면에 마른 발판 또는 안전 지점이 보이는 곳에만 둔다.
- 한 번 밀려도 3초 이내에 원래 진행 구간으로 돌아갈 수 있는 배치를 사용한다.
- 물살 중에도 키보드·조이스틱 입력을 유지한다.

## 6. 안전 위치와 재접속

- 서버는 플레이어가 마지막으로 확정한 유효 `safeAnchor`를 기준으로 삼는다.
- 깊은 물 진입 시 그 앵커로 되돌리고 1,500ms 동안 물살 재적용을 막는다.
- 저장 위치가 깊은 물, blocker, 닫힌 문 안이면 재접속 시 가장 가까운 유효 앵커로 복원한다.
- 물살 도중 연결이 끊기면 클라이언트 예상 좌표가 아니라 마지막 서버 확정 위치를 사용한다.
- 두 플레이어가 같은 물살에 있어도 cooldown, 연속 적용 수, 안전 앵커를 서로 공유하지 않는다.

새 DB 테이블·컬럼은 만들지 않는다. 기존 위치·방 상태 저장 구조에서 처리한다. 구조상 불가능한 부분이 확인되면 임의 스키마를 추가하지 말고 보고한다.

## 7. 클라이언트 표시

- 서버가 내려준 물살 구역에 `current-flow`를 배치한다.
- 정지 화면에서도 곡선 결로 흐름 방향을 읽을 수 있어야 하며 화살표·개발 좌표·디버그 글자를 사용자 화면에 표시하지 않는다.
- 물살 적용 시 짧은 위치 보간, 1회 흔들림, 작은 물방울 효과를 사용한다.
- 깊은 물 복귀 안내는 한 탐험 세션에서 처음 한 번만 표시한다.

```text
깊은 물은 위험해. 물풀이 잔잔한 길로 가자.
```

- 목표 문구는 다음을 사용한다.

```text
물결북의 파문을 따라 물풀 미로를 지나가자.
```

- 640×360에서 조이스틱·상호작용 버튼·목표 패널이 문과 방향 단서를 가리지 않게 한다.
- C2-1에서 관찰된 모바일 물들이 일부 가림은 이번 동선에 영향을 줄 때만 최소 보정한다. 정착지 전체 레이아웃을 다시 설계하지 않는다.

## 8. 시험

### 서버·단위 시험

1. 물결북 사건 전 문이 닫히고 통과할 수 없음
2. 물결북 사건 뒤 `lake_safe_route_opened` 1회 기록과 문 개방
3. 사건의 선행 조건·멱등·동시 요청
4. 물살 밖 이동은 기존 결과와 동일
5. 물살 안에서는 서버 데이터의 방향·거리만 적용
6. 위조 물살 ID·방향·거리 입력으로 결과를 바꿀 수 없음
7. 동일 물살 cooldown과 연속 적용 상한
8. 충돌·깊은 물 목적지의 통행 가능 위치 보정
9. 깊은 물 진입 시 안전 앵커 복귀와 진행 손실 없음
10. 잘못된 저장 위치의 재접속 보정
11. 두 플레이어의 물살 상태 독립
12. 세 에셋 키와 파일 존재, 닫힘·열림 렌더 상태

### 최소 E2E

`lake.e2e.ts` 또는 동일한 최소 호수 필터로 다음을 검증한다.

- 1280×720 키보드: 문 개방 → 약한 물살 → 마른 발판 도착
- 640×360 조이스틱: 방향 단서 → 물살 뒤 입력 유지 → 깊은 물 복귀
- 새로고침: 열린 문과 유효 안전 위치 복원
- 두 플레이어: 동일 물살 판정이 서로 독립

기존 테스트 도우미로 만들 수 없는 장면을 위해 운영 UI에 순간이동·사건 주입 버튼을 추가하지 않는다.
